# ループ運用ポリシー

## このリポジトリでループが担う範囲

**ループは `agent:pr` ラベルの issue を1件、実装して PR を作るところまで担う。**

このリポジトリは完了条件を機械判定できる（rspec / rubocop / steep / brakeman / bundler-audit）。
だから issue をゴールに固定して自走できる。

| ループがやる | ループがやらない |
|---|---|
| `agent:pr` issue の実装 〜 PR 作成 | ラベルの付与・変更 |
| 機械判定ゲートによる自己検証 | PR のマージ |
| 停止条件に当たったときの報告 | issue に書かれていないスコープへの拡大 |
| `.claude/state/loop.md` の更新 | 仕様そのものの決定 |

この範囲を広げたくなったら、ルールを書き換える前に人間に相談すること。

## 1. 1周につき1 issue

PR を作ったらその周は終了する。次の issue は次のトリガーで扱う。

連続で処理すると、レビュー未の PR が積み上がって人間の理解が追いつかなくなる
（Comprehension Debt）。また暴走したときの被害が1件に収まらない。

## 2. 状態はセッションの記憶より優先する

ループの2回目以降は前回の記憶がない状態で始まる。作業の開始時に
`.claude/state/loop.md` を読み、終了時に必ず更新すること。
**記憶とステートファイルが食い違ったら、ステートファイルが正。**

起動時に、state に載っている issue が実在してオープンかを確認し、
既にクローズされているものは掃除する。この掃除を飛ばすと、
存在しない issue を延々と拾い続ける（State Rot）。

`.claude/state/loop.md` は**どの issue の契約でも更新してよい例外**とする。
ループの記帳であって issue の成果物ではないため、「触ってよいファイル」に
書かれていなくても更新し、feature ブランチにコミットして PR に含める。

git 追跡下に置いているのは、Routines やクラウドセッションが fresh clone で
動くため。追跡外にすると毎回空の状態から始まり、
「エージェントは忘れるが、リポジトリは忘れない」が成立しなくなる。

## 3. 自律度ラベルに従う

issue のラベルで扱いが変わる。**ラベルの付与・変更は人間の専権事項**で、
Claude が自分で付け替えてはいけない（`settings.json` の deny でも禁止している）。

| ラベル | 振る舞い |
|---|---|
| `agent:pr` | 実装 → 検証 → PR 作成まで自走する。マージはしない |
| `agent:draft` | 調査して issue にコメントするのみ。**ファイルは作らない** |
| `human` | 一切触らない |
| `blocked` | 人間の判断待ち。触らないが、滞留が24時間を超えたら報告する |
| ラベルなし | 着手しない。推奨ラベルを1行コメントするに留める（上限あり） |

ラベルなしが多いのは正常な状態。無理にラベルを付ける必要はない。

## 4. 停止条件

**「迷ったら止まる」は主観なので無人では判定できない。** 以下の機械的な条件だけを
停止条件とし、どれにも当たらない場合は自分で決めて進むこと。

| 条件 | 止まり方 |
|---|---|
| 契約のプレフライト検査に不合格 | 着手せず issue に1コメント |
| API 案件なのに issue 本文に仕様が無い | 着手せず issue に1コメント |
| `gate-verifier` が3回連続不合格 | draft PR を出して停止 |
| `guideline-reviewer` の 🔴 必須 指摘が3回で解消しない | draft PR を出して停止 |
| issue の「触ってはいけないファイル」の変更が必要になった | draft PR を出して停止 |

**試行上限は3回。** 超えたら必ず止まる。無限リトライは人間に届かない（Escalation Failure）。

### 着手前は issue、途中は draft PR

作業が残っているのに issue コメントだけで終わると、ブランチが放置されて
次のループが拾えなくなる。draft PR なら CI が回り、人間が続きから引き取れ、
通知も1ヶ所に集まる。

draft PR の本文には必ず書くこと。

- `gate-verifier` の出力（通ったゲート / 通らなかったゲート）をそのまま
- 止まった分類（契約の欠陥 / 実行の失敗）
- 試行回数
- **人間に必要な判断を選択肢の形で1つだけ。** 「どうしますか」ではなく「A か B か」

issue には `blocked` を**提案**するコメントを1件だけ残す。ラベルは付けない。

## 5. 差分の最小性

issue の「触ってよいファイル」の外に手を出さない。
「ついでに直しておく」「気になったのでリファクタした」はしない（Over-Reach）。

触る必要が出たら、それは issue の契約の欠陥。実装を続けず停止条件に従う。

## 6. 投稿系には必ず件数上限を入れる

**1回の実行で issue にコメントできるのは最大3件。**

上限なしで回すとオープン issue 全件に一斉投稿され、通知が埋まって以降の
本当のエスカレーションが読まれなくなる（Notification Fatigue）。

- 一度コメントした issue には再投稿しない（`.claude/state/loop.md` に記録する）
- 4件以上該当した場合は、投稿せず**件数だけ報告**する

## 7. 実装の根拠

実装の作法はこのファイルに書かない。**単一の情報源は `docs/` 側**。

- `docs/development/implementation-guidelines.md` — アーキテクチャ制約・禁止事項・命名ルール
- `docs/development/directory.md` — 各層の責務・呼び出し関係・判断基準
- `docs/api/**` — 実装済み API の仕様書。**新規・変更のときは issue が正**で、
  docs は実装と同じ PR で更新する

実装前に必ず上2つを読むこと。ここにコピーを作ると、docs と食い違ったときに
**高い遵守率のまま間違いを実行する**ことになる。

## 8. 並列実行

現時点では並列実行しない（1周1 issue のため衝突しない）。
並列で回す必要が出た場合は `git worktree` で issue ごとに作業ツリーを分離すること。
同じツリーで複数のループを走らせない（Parallel Collision）。
