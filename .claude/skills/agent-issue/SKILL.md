# agent-issue スキル

`/implement-issue` が無人で実装できる形の issue を起票する。

**このスキルの本体はヒアリングではなく「曖昧な要望を機械判定可能な完了条件に翻訳すること」。**
テンプレートを埋めるだけなら GitHub の Web UI で足りる。ここで価値が出るのは、
「ちゃんと動くようにして」を `rails routes | grep` に落とすところ。

---

## Step 1: 何をしたいか聞く

引数 `$ARGUMENTS` があればそれを出発点にする。無ければ聞く。

この時点では曖昧でよい。曖昧なものを詰めるのがこのスキルの仕事。

## Step 2: リポジトリを調べる

**ユーザーに聞く前に、自分で分かることは調べる。** 聞く回数を減らすため。

- 関連しそうな既存ファイル（`app/` `spec/` `config/routes.rb`）
- API に関わるなら `docs/api/**` に仕様書があるか
- 似た実装が既にあるか（あれば「触ってよいファイル」の当たりが付く）

### 仕様書が無い API 案件は起票を止める

API の追加・変更なのに `docs/api/**` に仕様書が無い場合、
**この issue を起票してもループは着手できず差し戻される。**

その場合はここで止めて、`/api-spec-review` で先に仕様を固めることを提案する。

## Step 3: 完了条件を機械判定可能な形に翻訳する

**ここが一番重要。** ユーザーの言葉をそのまま完了条件にしない。

| ユーザーの言葉 | 翻訳後 |
|---|---|
| ちゃんと動くようにして | `docker compose exec web bundle exec rails routes \| grep 'v1/xxx'` が GET を返す |
| テストを書いて | `spec/requests/v1/xxx_spec.rb` が存在し、200 / 401 / 404 をカバーしている |
| ドキュメントも更新して | `docs/api/xxx/index.md` に `## レスポンス` セクションが存在する |
| エラーハンドリングして | 存在しない ID を渡したとき 404 と `error_code` を返す request spec が通る |
| リファクタして | 振る舞いが変わらないこと（既存 spec が無修正で通る） |

翻訳できないものは**完了条件にしない**。それは「やること」に書くか、issue を分割する。

### 5ゲートは書かない

rspec / rubocop / steep / brakeman / bundler-audit は `gate-verifier` が毎回実行する。
完了条件に書くと本質的な条件が埋もれるので書かない。
**この issue でしか確認できないこと**だけを書く。

### 差分のファイル数を固定しない

`git diff --name-only develop...HEAD` の出力が N 行、のような条件を書かない。
ループは終了時に必ず `.claude/state/loop.md` を更新するので、**差分は必ず1件増えて落ちる**。

スコープ逸脱を防ぎたい場合は「**禁止したいディレクトリに差分が無いこと**」の形にする。

| ✗ 壊れる書き方 | ✓ 正しい書き方 |
|---|---|
| `git diff --name-only develop...HEAD` が1行のみ | `git diff --name-only develop...HEAD \| grep -qE '^(app\|db\|spec\|config)/'` が失敗する |

## Step 4: 触ってよい / いけないファイルを決める

「触ってよいファイル」は**必要最小限**にする。広く取ると Over-Reach の余地が生まれる。
Step 2 の調査結果から具体的なパスを提案する。

「触ってはいけないファイル」は最低限これを含める。

```
- `db/migrate/**` — 適用済みマイグレーションの改変は禁止
- `.github/workflows/**` — CI の変更は別 issue
- `Gemfile` `Gemfile.lock` — 依存追加は人間の判断
- `.claude/settings.json` `.claude/hooks/**` `.claude/rules/**` — 強制層は人間の専権
```

**`.claude/**` とまとめて禁止しない。** `.claude/state/loop.md` はループが終了時に
必ず更新する記帳ファイルで、どの契約でも例外的に更新してよい（`loop-policy.md` §2）。
まとめて禁止すると、ループが着手できずに差し戻す。禁止したいのは強制層3つだけ。

## Step 5: エスカレーション条件を決める

**「ここに書かれていない迷いは、ループが自分で判断して進む」ことをユーザーに明示する。**

判断を委ねたくない論点があるかを必ず聞く。よくあるもの:

- 既存 API のレスポンス形式を変える必要が出た場合
- 仕様書と既存実装が食い違っていた場合
- 想定より広い範囲の変更が必要になった場合

最低限これは入れる: `3回試して完了条件を満たせない場合は draft PR を出して停止する`

## Step 6: 草案を提示して確認を取る

`.github/ISSUE_TEMPLATE/agent-task.yml` と同じブロック構成で組み立て、提示する。

```markdown
## 変更の種類
{新機能 / 既存改修 / 削除 / リファクタ / 設定・基盤}

## 背景
{なぜ必要か}

## やること
- {何を作る・変える・消すか}

## 完了条件
- [ ] {機械判定可能な条件}

## 触ってよいファイル
- `{パス}`

## 触ってはいけないファイル
- `{パス}` — {理由}

## エスカレーション条件
- {条件}

## 参考
- {仕様書・関連 issue}
```

## Step 7: 自己検査（起票前）

**提示した草案を、`/loop-triage` のプレフライト検査と同じ観点で自分で採点する。**
ここで弾いておかないと、起票後に差し戻されて二度手間になる。

| 検査項目 | 不合格の例 |
|---|---|
| 完了条件が機械判定可能か | 「正しく動く」「使いやすい」など、コマンドや存在確認に落ちていない |
| 「触ってよいファイル」があるか | 記載なし・`**/*` のような広すぎる指定 |
| 「触ってはいけないファイル」があるか | 記載なし・「特になし」 |
| エスカレーション条件があるか | 記載なし |
| 仕様が実在するか | API 案件なのに `docs/api/**` に該当仕様が無い |

**1つでも不合格なら起票しない。** 何が足りないかを示してユーザーに聞き直す。

検査結果は必ずユーザーに見せる。合格した項目も列挙すること。
「検査しました」だけでは、検査したかどうか分からない。

## Step 8: 起票する

```bash
gh issue create --title "{タイトル}" --body "{本文}"
```

タイトルは日本語で簡潔に（70文字以内）。動詞で終える（例: 「〜を追加する」「〜を削除する」）。

**ラベルは付けない。** 自律度ラベルの付与は人間の専権事項で、
`gh label` と `gh issue edit` は deny されている。

起票後、URL とあわせて**どのラベルを付けるべきかを1行で提案**する。

```
起票しました: {URL}
推奨ラベル: agent:pr（完了条件が機械判定でき、実装範囲が閉じているため）
→ ラベルを付けるまでループは着手しません。
```

---

## やってはいけないこと

- **翻訳できない完了条件をそのまま書く。** 「ちゃんと動く」を通すと、
  ループは自分の解釈で「動いた」と判断して PR を出す
- **「触ってよいファイル」を広く取る。** `app/**` のような指定は Over-Reach を招く
- **ラベルを付ける**（deny されている。提案までが仕事）
- **自己検査を飛ばして起票する**
- 1つの issue に複数の目的を詰める。分割する
