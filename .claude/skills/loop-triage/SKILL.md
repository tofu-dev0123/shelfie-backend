ループの**観測フェーズ**を担当する。仕事を見つけて**1件選ぶまで**が仕事。

**実装はしない。** 実装は `/implement-issue` の担当。
役割の違うものを1本のスキルに混ぜると、選別したいのか実装したいのか分からなくなる。

`.claude/rules/loop-policy.md` に従うこと。

## 手順

### 1. 状態を読む

`.claude/state/loop.md` を読む。ここが進捗の正であり、会話の記憶と食い違ったらこちらを信じる。

「対応中」に issue が載っている場合は、**新しい issue を選ばない**。
その issue の続きを報告して終了する（1周につき1 issue）。

### 2. キューを取得する

```bash
gh issue list --state open --limit 50 --json number,title,labels,updatedAt
```

### 3. 死んだ項目を掃除する（State Rot 対策）

`.claude/state/loop.md` の「対応中」「人間待ち」「試行回数」に載っている issue を
上のリストと突き合わせ、既にクローズされているものは「完了」へ移すか削除する。

**この掃除を飛ばすと、存在しない issue を延々と拾い続ける。**

### 4. ラベルで絞る

`.claude/rules/loop-policy.md`「3. 自律度ラベルに従う」の表に従う。

- `human` → 除外
- `blocked` → 除外。ただし `updatedAt` からの滞留が24時間を超えていたら報告する
- `agent:draft` → 今回は対象外（調査専用のため別途扱う）
- ラベルなし → 着手しない。コメントの扱いは下記
- **`agent:pr` のみが着手対象**

`agent:pr` が0件なら「着手候補: なし」と書いて手順7へ。**これは異常ではない。**

#### ラベル未設定 issue へのコメント（上限3件）

**1回の実行でコメントできるのは最大3件。** 上限なしで回すとオープン issue 全件に
一斉投稿され、通知が埋まって以降の本当のエスカレーションが読まれなくなる。

- `.claude/state/loop.md` の「ラベル提案済み」に載っている issue には再投稿しない
- 4件以上該当した場合は、投稿せず**件数だけ報告**する
- 投稿したら「ラベル提案済み」に記録する

コメントは1行。例: `推奨ラベル: agent:pr（完了条件が機械判定できる粒度のため）`

**ラベルを自分で付け替えてはいけない。** 提案のコメントを書くだけ。

### 5. 1件だけ選ぶ

優先順位は ①`updatedAt` が古いもの ②`blocked` から復帰したもの ③その他。

**複数選ばない。** 1周につき1 issue。

### 6. 契約のプレフライト検査

選んだ issue を `gh issue view {number}` で読み、以下を検査する。
**ここで弾けば1分で済む。** 途中まで実装してから止まるのが一番もったいない。

| 検査項目 | 不合格の例 |
|---|---|
| 「やること」があるか | 記載なし。完了条件だけでは何を作るのか分からない |
| 完了条件が機械判定可能か | 「正しく動くこと」「使いやすくすること」など、コマンドと期待結果に落ちていないもの |
| **完了条件が差分のファイル数を固定していないか** | 「`git diff --name-only` の出力が1行のみ」。ループは終了時に必ず state を更新するので、必ず1件増えて落ちる |
| 「触ってよいファイル」があるか | 記載なし・`**/*` のような広すぎる指定 |
| 「触ってはいけないファイル」があるか | 記載なし・「特になし」 |
| **契約が state 更新を禁止していないか** | 「触ってはいけないファイル」に `.claude/**` とまとめて書かれている。`.claude/state/loop.md` はどの契約でも更新してよい例外 |
| エスカレーション条件があるか | 記載なし |
| API 案件なら issue 本文に仕様があるか | エンドポイント / メソッド / 認証 / リクエスト / レスポンス / エラーのどれかが issue に書かれていない。**`docs/api/**` に無いことは不合格理由にならない**（新規 API では docs は実装と同じ PR で作られるため） |
| API 案件なら docs 更新が契約に入っているか | 「触ってよいファイル」に該当する `docs/api/**` が無い。これが無いと差分の最小性（`loop-policy.md` §5）と衝突して実装できない |

太字の2項目は、**ループ自身の記帳と契約が衝突しないか**の検査。
これを見落とすと、着手してから Step 4 で気づくことになり、その分が無駄になる。

検査項目は `.github/ISSUE_TEMPLATE/agent-task.yml` の必須ブロックと対応している。
起票時に `/agent-issue` を使えばここは通るはずなので、**弾かれる issue が続く場合は
テンプレートかスキル側に原因がある**。「次回への申し送り」に記録すること。

**1つでも欠けたら着手しない。** issue に不足箇所を1コメントし、`blocked` を提案して終了する
（ラベルは付けない）。この件を `.claude/state/loop.md` の「次回への申し送り」に記録する。
溜まったものが issue テンプレートの改善点になる。

### 7. 状態を書き戻す

`.claude/state/loop.md` を更新する。最低限これを書く。

- 最終実行の日時（`date +%F` で取得。推測で書かない）
- 「対応中」に着手する issue（着手する場合）
- この実行でコメントした issue を「ラベル提案済み」に追記
- プレフライト検査で弾いた件を「次回への申し送り」に追記

#### コミット先

**着手する場合**（`/implement-issue` に続く）は、ここではコミットしない。
feature ブランチ上で `implement-issue` Step 13 がまとめてコミットする。

**トリアージだけで終わる場合**は feature ブランチが存在しないので、
`develop` を dirty にしたまま放置しない（次の周の `git status` チェックで止まる）。

まず**実質的な変更があったか**を判定する。

```bash
git diff --stat .claude/state/loop.md
```

- **最終実行日しか変わっていない** → コミットしない。`git checkout -- .claude/state/loop.md` で戻す。
  日付だけの PR を毎周作ると通知が埋まる（Notification Fatigue）
- **それ以外の変更がある**（差し戻し記録・ラベル提案・blocked の増減・申し送り）→ 専用ブランチで PR を出す

```bash
git checkout -b "chore/loop-state-$(date +%Y%m%d-%H%M)"
git add .claude/state/loop.md
git commit -m "chore: ループの記帳を更新する"
git push -u origin HEAD
gh pr create --base develop --title "chore: ループの記帳を更新する" \
  --body "トリアージのみの周の記帳。差し戻した issue と申し送りを記録する。"
```

**`develop` に直接コミットしない。** ブランチ運用を崩さないため。

### 8. 報告する

5行以内。

```
着手候補: #NN <タイトル>（または「なし」）
契約検査: 合格 / 不合格（<不足していた項目>）
人間待ち: #NN（<待っている判断>、滞留 <N> 時間）
ラベル未設定: N 件（うちコメント N 件 / 上限超過で見送り N 件）
```

着手候補があり契約検査に合格した場合は、続けて `/implement-issue #NN` を実行してよい。

## やってはいけないこと

- **選んだ issue の実装や調査を続けて始める**（選ぶまでがこのスキル）
- **ラベルを自分で付け替える**（人間の専権事項）
- **`.claude/state/` 以外のファイルを作成・編集する**
- 一度に複数の issue を選ぶ
- 「着手候補: なし」を問題として扱う。**それが通常の状態**
