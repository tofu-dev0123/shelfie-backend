# 認証フロー

## 認証が必要な操作

| 操作 | ログイン |
|---|---|
| 本棚・書籍・ユーザーの閲覧 | 不要 |
| 投稿・編集・削除・いいね・フォロー | 必須 |

---

## 認証方式の選定理由

### なぜ Clerk を使うか

- パスワードのハッシュ化・保管・リセットフローなどのセキュリティ実装を Clerk に委譲できる
- ユーザーがパスワードを覚える必要がなく、ログイン UX が簡素化される
- Google OAuth などの外部プロバイダー連携をシンプルな設定で実現できる

### なぜバックエンド独自の JWT を発行するか

Clerk JWT をそのまま API 認証に使い続けると以下の問題がある。

- **プロバイダー依存** — 将来 Clerk から別の認証基盤へ移行した場合、API 側の検証ロジックに影響が出る
- **強制ログアウト不可** — Clerk が発行したトークンはバックエンド側から無効化できない

そのため、バックエンドが Clerk JWT を**一度だけ検証**し、独自の JWT を発行する。
以降の API リクエストはバックエンド独自のトークンで認証を完結させる。

## 認証フロー（ログイン）

```
┌─────────────┐         ┌───────────┐         ┌─────────────────┐
│   Next.js   │         │   Clerk   │         │   Rails API     │
└──────┬──────┘         └─────┬─────┘         └────────┬────────┘
       │                      │                         │
       │  ① Google ログインボタン押下                    │
       │─────────────────────>│                         │
       │                      │                         │
       │  ② Google 認証完了・Clerk セッション確立        │
       │<─────────────────────│                         │
       │                      │                         │
       │  ③ Clerk JWT をバックエンドに送信               │
       │──────────────────────────────────────────────> │
       │                      │                         │
       │                      │  ④ Clerk JWT を検証（1回のみ）
       │                      │    clerk_user_id・email を取得
       │                      │                         │
       │                      │     ⑤ User レコード取得 │
       │                      │     ⑥ アクセストークン + リフレッシュトークンを発行
       │                      │     ⑦ リフレッシュトークンを DB に保存
       │                      │                         │
       │  ⑧ アクセストークン（レスポンスボディ）          │
       │     リフレッシュトークン（HttpOnly Cookie）      │
       │<────────────────────────────────────────────── │
       │                      │                         │
       │  ⑨ アクセストークンをメモリに保存               │
```

> 新規ユーザーの場合は、ログイン前にプロフィール設定（nickname / username の入力）を経て User レコードを作成します。詳細は [サインアップフロー](./signup.md) を参照してください。

## 2トークン方式

「ログインしっぱなし」の UX を実現するため、有効期限の異なる 2 種類のトークンを運用します。

| トークン | 有効期限 | 保存場所 | 用途 |
|---|---|---|---|
| アクセストークン | 60 分 | **メモリ（JS変数）** | API リクエストの認証 |
| リフレッシュトークン | 30 日 | **HttpOnly Cookie** | アクセストークンの再発行 |

### アクセストークンをメモリに保存する理由

localStorage は XSS 攻撃でスクリプトから読み取られるリスクがある。
メモリ（JS変数）に保存することでそのリスクを排除する。
ページリロード時はリフレッシュトークンを使って自動的に再取得する。

### リフレッシュトークンを HttpOnly Cookie に保存する理由

HttpOnly Cookie は JavaScript からアクセスできないため、XSS 攻撃でトークンが盗まれるリスクを防げる。

## トークン再発行フロー（サイレントリフレッシュ）

アクセストークンが期限切れになった場合、ユーザーに意識させることなく自動で再発行します。

```
Next.js                              Rails API
  │                                      │
  │  APIリクエスト（期限切れのアクセストークン）
  │─────────────────────────────────────>│
  │                                      │
  │  401 Unauthorized                    │
  │<─────────────────────────────────────│
  │                                      │
  │  リフレッシュリクエスト（HttpOnly Cookie のリフレッシュトークン）
  │─────────────────────────────────────>│
  │                                      │ DBでリフレッシュトークンを検証
  │                                      │ 有効期限・存在確認
  │  新しいアクセストークン               │
  │<─────────────────────────────────────│
  │                                      │
  │  元のAPIリクエストをリトライ          │
  │─────────────────────────────────────>│
```

### リフレッシュトークンが期限切れの場合

```
Next.js                              Rails API
  │                                      │
  │  リフレッシュリクエスト               │
  │─────────────────────────────────────>│
  │                                      │ リフレッシュトークンが期限切れ
  │  401 Unauthorized                    │
  │<─────────────────────────────────────│
  │                                      │
  │  Googleログイン画面へリダイレクト     │
  │  （ユーザーが再ログイン）             │
```

## refresh_tokens テーブル

リフレッシュトークンをDBで管理することで、デバイスごとの個別ログアウトと強制ログアウトを実現します。

| カラム | 型 | 用途 |
|---|---|---|
| `id` | PK | |
| `user_id` | FK | どのユーザーか |
| `token` | string | トークンの値（ユニーク） |
| `expires_at` | datetime | 有効期限 |
| `created_at` | datetime | 発行日時 |

### デバイスごとの管理

ログインのたびにレコードが1件作成されるため、複数デバイスでのログインを個別に管理できます。

| 操作 | DB の操作 |
|---|---|
| ログイン | レコードを作成 |
| ログアウト（1デバイス） | そのデバイスのレコードを削除 |
| 全デバイスログアウト | user_id に紐づく全レコードを削除 |
