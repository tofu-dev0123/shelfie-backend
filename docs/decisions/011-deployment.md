# 011: 本番デプロイ方式（GitHub Actions + SSM Run Command）

## 決定日

2026-08-15（issue #159 の実施方針の検討で確定）

## ステータス

決定済み

## 背景

[010: ホスティング先](./010-hosting.md) は副次的な決定として **「デプロイは Kamal 2.11 を使う」**
と記録していた。理由は「ゼロダウンタイム切替とロールバックが標準で付いてくる」ことだった。

その構成を実際に組む段階で、**Kamal が要求するものが3つ判明した。**

| Kamal が要求するもの | この構成での意味 |
|---|---|
| **SSH 接続** | SSM ネイティブの transport が無いため、ingress 0 の構成では SSM ProxyCommand + デプロイ用鍵ペアが要る |
| **新旧2コンテナの同時起動** | ゼロダウンタイム切替の仕組みそのもの。1GB の箱でメモリのピークを作る |
| **デプロイ元での秘密の評価** | `.kamal/secrets` はデプロイ元（GitHub Actions ランナー）で評価されるため、**全14個の秘密がランナーを通過する** |

**これらはいずれも Kamal を使うことによって発生するもので、要件から出たものではない。**

---

## 決定内容

**Kamal を使わない。GitHub Actions でイメージをビルドし、SSM Run Command で
EC2 にシェルスクリプトを実行させてコンテナを差し替える。**

```
GitHub Actions（ubuntu-24.04-arm）
  ├ docker build / push → GHCR
  └ OIDC → AssumeRole → ssm:SendCommand
                            │  ★ ランナーは EC2 に直接接続しない
                            ▼
                        SSM Agent（EC2 が外向きに張った接続で受信）
                            ├ Parameter Store から app.env を生成（インスタンスロール）
                            ├ GHCR から docker pull
                            └ docker rm -f && docker run
```

| 項目 | 決定 |
|---|---|
| デプロイの実行主体 | **GitHub Actions**（`workflow_dispatch` による手動） |
| EC2 への到達手段 | **SSM Run Command**（SSH を使わない） |
| コンテナの実行 | **`docker run` + `--restart unless-stopped`**（compose を使わない） |
| ゼロダウンタイム | **捨てる。** デプロイ中 10〜20秒の 502 を受け入れる |
| ロールバック | 前のイメージタグを指定して同じワークフローを再実行する |

---

## Kamal を外して得るもの

**得るものが3つ、失うものが1つ。** これが決定の全体である。

### 1. SSH 鍵の配布が不要になる

SSM Run Command は **IAM 認証だけで完結する。** 鍵という概念が登場しない。

ADR 010 は「SSM は分散を減らす方向に働く」ことを Lightsail ではなく EC2 を選んだ理由に挙げていたが、
**Kamal を残すとその利点が SSH の要求で相殺されていた。**

### 2. ADR 010 が挙げていた最大のリスクが解消される

ADR 010 の「認識しているリスク」より:

> **1GB でのゼロダウンタイム切替** — 切替中に Rails が2つ並ぶ。
> 概算で 300MB×2 + proxy 30MB + OS/Docker 250MB ≈ **880MB / 1024MB**

**このリスクはゼロダウンタイム切替の仕組みそのものに由来する。**
新旧2コンテナが並ばず、`kamal-proxy` も常駐しないため、概算で **約 580MB** に下がる。

> **上記はいずれも概算であり実測値ではない。** 実測は #159 で行う。

これにより ADR 010 が保険として挙げていた **`t4g.small` への引き上げ（月 +$2.32）が不要**になる見込み。

### 3. 秘密が GitHub Actions を通らない

`.kamal/secrets` はデプロイ元で評価されるため、Kamal を使うと
`DATABASE_URL` から OAuth の `client_secret` まで**全14個がランナーのメモリと環境変数を通過する。**

SSM Run Command なら **EC2 がインスタンスロールで Parameter Store から直接取得する。**
ランナーが持つのは「コマンドを送る権限」だけで、**秘密を1つも見ない。**

漏洩時の影響範囲が、ランナーのログ・サードパーティ Action・ワークフローの改変から切り離される。

## 失うもの

### ゼロダウンタイム

デプロイ中に **10〜20秒の 502** が発生する。

**利用者は自分1人、閲覧者は数人**（ADR 010 の前提）で、デプロイは週に数回。
この断が誰かに当たる確率は実質ゼロと判断した。

ADR 010 が Cloud Run と Cloudflare Containers を「コールドスタートで訪問者を待たせる」として
却下したことと矛盾しない。あちらは**リクエストごとに毎回起きる**話で、
デプロイ時の一時的かつ制御された断とは性質が違う。

### 壊れたイメージを出したときの自動保護

Kamal はヘルスチェックが通らなければ旧コンテナを残す（既定 `deploy_timeout` 30秒）。
`docker run` にはこの保護が無く、**壊れたイメージを出すとサイトが落ちる。**

緩和策を3つ置く。

- CI の5ゲートを通ったコミットのイメージだけをデプロイ対象にする
- デプロイ後に **公開 URL（`https://api.shelfie.jp/up`）を叩いて検証する**
  — オリジンの `localhost:8080` を叩くと Tunnel の死を見逃すため
- ロールバックは前のタグを指定して再実行するだけ（1操作）

**「壊れたまま気づかない」は防げる。「壊れている間サイトが落ちている」は残る。**

---

## 却下した案

| 案 | 却下理由 |
|---|---|
| **Kamal を継続** | 得るもの1つ（無停止）に対し、SSH 鍵・メモリピーク・秘密の経路という**独立した3つの問題**を引き受けることになる |
| **docker compose** | コンテナが1つ（cloudflared は systemd）なので宣言的記述の利点が出ない。`.env` と `env_file` の役割の違いという compose 固有の落とし穴だけが残る |
| **EC2 上で git pull してビルド** | 1GB の箱で `bundle install` が OOM する |
| **ローカル Mac から手動デプロイ** | Apple Silicon なので arm64 ネイティブビルドができ最も手軽だが、**実行の記録が残らない。** スキーマ変更や本番反映の履歴を追えなくなる |

---

## 副次的な決定

### 秘密は SSM Parameter Store に置く

ADR 010 が未決としていた「秘密の管理方法」をここで決める。

| | Parameter Store（Standard） | Secrets Manager |
|---|---|---|
| 費用 | **$0** | **$0.40 / シークレット / 月** |
| 暗号化 | SecureString（AWS 管理キーは無料） | 同等 |
| 自動ローテーション | なし | あり |

秘密は14個前後になるため、Secrets Manager では **月 $5.6** となり
ADR 010 の予算 $13.45 の **42%** を占める。1つの JSON にまとめれば $0.40 に抑えられるが、
**1つの値を変えるのに JSON 全体を書き換える**ことになる。

自動ローテーションは RDS などの統合が前提の機能で、OAuth の `client_secret` は自動化できない。
**払う理由が無い。**

**`SecureString` は CloudFormation で作成できない**（`AWS::SSM::Parameter` の `Type` は
`String` / `StringList` のみ）。この制約を分離線として利用し、
**秘密は手作業で投入、非秘密は CFN で管理**する。テンプレートが git に入るため、
**秘密が書けない方が安全**である。

### マイグレーションは専用ワークフローで手動トリガーする

`bin/docker-entrypoint` はコンテナ起動のたびに `db:prepare` を実行していた。**これを削除する。**

起動時の自動適用には、この構成で無視できない問題が5つある。

| # | 問題 |
|---|---|
| 1 | 承認ゲートを置いても**デプロイ経路から素通りする** |
| 2 | マイグレーション失敗とアプリ起動失敗が**「コンテナが上がらない」に潰れる**（対処は正反対なのに） |
| 3 | 接続先を誤ると **`schema.rb` を流し込んで「デプロイ成功」に見える**。`/up` は DB を触らないため健全性チェックにも掛からない |
| 4 | Neon のスケールゼロからの復帰とシンガポール往復が**起動のクリティカルパスに乗る** |
| 5 | スキーマ変更の記録が**コンテナの STDOUT にしか残らない** |

手動ワークフローなら、実行の記録が GitHub Actions の履歴に**実行者・コミット・承認者つきで恒久的に残る。**

「マイグレーション忘れ」は**適用するのではなく検知する**ことで防ぐ。
デプロイスクリプトが `db:migrate:status` で未適用を確認し、あれば止める
（expand / contract 手順のためのスキップ入力は用意する）。

### ワークフローは3本に分ける

ビルドを独立させないと、**migrate の実行時点でイメージが存在しない**という順序の問題が起きる。

| ファイル | トリガー | 承認 |
|---|---|---|
| `build.yml` | `push: main`（自動） | なし |
| `migrate.yml` | `workflow_dispatch` | **必須** |
| `deploy.yml` | `workflow_dispatch` | なし |

**承認は「戻せるかどうか」で置く。** スキーマ変更だけが不可逆なので、そこにだけゲートを掛ける。

GitHub Environments の名前を IAM の信頼ポリシーの `sub` 条件に使うため、
**承認を通らないと OIDC トークンが発行されず AssumeRole できない。**
ワークフローの YAML を書き換えても迂回できない。

### cloudflared は systemd で常駐させ、コンテナにしない

デプロイ操作が**外部からの到達性そのものを巻き込まない**ようにするため。

アプリが落ちていても Tunnel が生きていれば 502 が返り、
「サーバは生きているがアプリが死んでいる」と外から判別できる。
Tunnel ごと落ちると Cloudflare の 1033 になり、原因の候補が広がる。

### `secret_key_base` は `SECRET_KEY_BASE` 環境変数で供給する

`config/master.key` は失われており `config/credentials.yml.enc` は復号できない。
一方で **credentials を読む実コードは1行も存在しない**（ADR 009 で認証情報は ENV に統一済み）。

`ENV["SECRET_KEY_BASE"]` は credentials より優先されるため、
**credentials を復活させずに供給できる。** 秘密を1つ増やす理由が無い。

> **`secret_key_base` は Shelfie の認証システム全体の唯一の署名鍵である**
> （access / refresh / signup / oauth_state の4種すべて）。
> フレームワークの汎用鍵と認証の鍵が同一になっている点は設計上の弱さだが、
> **その分離は別 issue で扱う。**

### イメージは GHCR に public で置く

EC2 側の `docker login` を不要にするため。private にすると
**PAT を Parameter Store に置き、期限切れのたびに更新する**運用が発生する。

リポジトリが public なのでイメージを private にしても隠れるものは無い
（`.dockerignore` が `.env*` と `config/master.key` を除外していることは確認済み）。

ビルドは **`ubuntu-24.04-arm` ランナー**で行う。public リポジトリでは無料で、
`t4g`（Graviton）向けの arm64 イメージが**ネイティブでビルドされる**（QEMU が挟まらない）。

## 認識しているリスク

| リスク | 内容 | 対処 |
|---|---|---|
| **デプロイ中の断** | 10〜20秒の 502 | 受け入れる。実測して記録する |
| **壊れたイメージで全断** | ヘルスチェックによる自動保護が無い | CI 5ゲート + デプロイ後の公開 URL 検証 + 即時ロールバック |
| **`docker rm -f` の非可逆性** | 旧コンテナは停止ではなく削除される | イメージは GHCR に残るのでタグ指定で復元できる |
| **ワークフローの改変** | Actions を書き換えれば任意のコマンドを EC2 で実行できる | `ssm:SendCommand` はドキュメントとインスタンスを限定。**秘密は読めない** |

---

## 未決の論点

**この ADR では決めない。**

- **バックアップ方針**（Neon 側に委ねる範囲と自前で取る範囲）— ADR 010 から引き続き未決
- SCP によるリージョン制限 — グローバルサービスの扱いで詰まる可能性があり、稼働後に検討する
- ビルドキャッシュ（`type=gha`）— ビルドはデプロイのクリティカルパスから外れているため、遅いと感じてから
- GHCR の古いイメージの保持ポリシー — public パッケージのストレージは無料のため当面放置
- **JWT の署名鍵を `secret_key_base` から分離すること** — 別 issue

## 再検討のトリガー

- **デプロイ中の断が許容できなくなったとき**（利用者が増え、SLA が必要になったとき）
- **1GB で OOM が発生したとき** — `t4g.small` への変更を検討し、
  **総額が $20 を超えるなら ADR 010 の前提が崩れる**ので新しい ADR を起票する
- コンテナが2つ以上になったとき — `docker run` の羅列より compose が有利になる
- 複数台構成にするとき — この決定は1台であることに強く依存している
