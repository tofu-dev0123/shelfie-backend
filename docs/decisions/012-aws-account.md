# 012: AWS アカウント構成（Shelfie 専用のメンバーアカウント）

## 決定日

2026-08-15（issue #159 の実施方針の検討で確定）

## ステータス

決定済み

## 背景

Shelfie を [010](./010-hosting.md) の構成で AWS に載せるにあたり、
**どのアカウントに置くか**を決める必要が生じた。

既存の AWS アカウントを棚卸ししたところ、次の状態だった。

| 項目 | 実態 |
|---|---|
| AWS Organizations | **有効**（FeatureSet `ALL` / SCP 有効） |
| IAM Identity Center（SSO） | **利用中** |
| **メンバーアカウント** | **0件** |
| 同居しているプロジェクト | `tofu-blog` / `tottoku` / IaC 学習用の Terraform state / CDK ブートストラップ |

つまり **組織は作られているが、すべてのワークロードが管理アカウントの中で動いている。**

過去にこの同居が実際に問題を起こしている。2026-08-02 に Shelfie のアバター機能を削除した際、
「Shelfie が使うのは S3 だけ」という前提でリソースを一斉削除しかけ、
棚卸しによって**他プロジェクトのリソースが多数見つかって中止**した経緯がある。

---

## 決定内容

**Shelfie 専用のメンバーアカウントを組織配下に新規作成し、本番リソースをすべてそこに置く。**

```
Organization
├── 管理アカウント          ← 請求と組織管理に専念させていく
│     └ 既存: tofu-blog / tottoku / 学習用リソース（今回は移設しない）
└── shelfie-prod            ← 新規。Shelfie の本番リソース
```

| 項目 | 決定 |
|---|---|
| 位置づけ | **組織配下のメンバーアカウント**（単独アカウントにしない） |
| アカウント名 | `shelfie-prod` |
| ルートメール | 個人開発用アドレスの `+shelfie-prod` エイリアス |
| 管理者アクセス | **IAM Identity Center（SSO）の permission set** |
| 緊急用の経路 | `OrganizationAccountAccessRole`（**既定名のまま。削除しない**） |
| 既存ワークロードの移設 | **行わない。** 段階的に分離できる |
| ステージング用アカウント | **今は作らない** |

---

## なぜ管理アカウントにワークロードを置かないか

**管理アカウントには他と決定的に違う性質が1つある。**

| | 管理アカウント | メンバーアカウント |
|---|---|---|
| **SCP が適用されるか** | **されない**（自分自身には効かない） | される |
| 請求・組織全体の権限 | **集中している** | 持たない |
| 侵害されたときの影響範囲 | **組織全体** | そのアカウントのみ |

**SCP というガードレールを唯一かけられないアカウント**で本番サービスを動かしている状態だった。
`FeatureSet: ALL` で SCP を有効にしているにもかかわらず、その恩恵が及ばない。

## 分離によって単純になるもの

アカウントを分けると、**共用を前提に組んでいた回避策が3つ不要になる。**

| 共用のままなら必要だったもの | 分離後 |
|---|---|
| GitHub OIDC provider を既存の共用のものから参照する（**1アカウントに1つしか作れない**ため CFN で作成できない） | **CFN でリソースとして作れる。** スタックが自己完結する |
| スタック削除時に他プロジェクトの OIDC provider を巻き込まない配慮 | 不要 |
| `ssm:SendCommand` に他プロジェクトのインスタンスを守るタグ条件を必須にする | 構造的に不要（多層防御として残すのは可） |

加えて、**コストがアカウント単位でそのまま実測値になる。**
ADR 010 は月 $13.45 という想定を管理する話なので、按分の見積もりが要らなくなる意味は大きい。

---

## 却下した案

### A. 共用アカウントのまま置く

**追加コストがゼロという利点しかない。** 上記の SCP・回避策・コスト可視性のすべてを失う。

そして **リソースをまだ1つも作っていない今が、分離の最も安いタイミング**だった。
EC2 を作ってから移すのは移設作業になる。

### B. 組織に属さない単独アカウントを作る

**最大 $200 のクレジットが得られるが、成立しない。**

| 問題 | 内容 |
|---|---|
| **クレジットは組織参加で失効する** | 単独のままでなければ受け取れない。後から組織に入れた時点で失効する |
| **IAM Identity Center が使えない** | SSO は組織が前提。**「SSO で管理できるから分離しやすい」という前提そのものが崩れる** |
| **Free プランは自動クローズされる** | 開設から6ヶ月、またはクレジットを使い切った時点で**アカウントが閉じられる**（有料プランに変換しない場合）。本番運用に適さない |
| 請求が分かれる | 支払い方法を別途登録することになる |

$200 は約15ヶ月分のインフラ費用に相当するが、**一度きり**である。
対して SSO による管理のしやすさと請求の一本化は**運用が続く限り効き続ける。**

### C. 環境ごとにアカウントを分ける（prod / stg を同時に作る）

**ステージング環境の要件がまだ無い。** アカウントを増やすと、
SSO の割り当て・Budget・CLI プロファイルといった初期設定がその数だけ増える。

**必要になってから作る。** アカウント名に `-prod` を含めたのは、
そのとき `shelfie-stg` を素直に足せるようにするため。

---

## 副次的な決定

### `OrganizationAccountAccessRole` は既定名のまま使う

改名しても安全性は上がらない。**守っているのは名前ではなく管理アカウント側の IAM 権限**であり、
名前を変えるのは推測されにくくするだけで実質的な効果が無い。
アカウントが増えたときに全アカウントで同じ名前である方が、切り替え手順が1つで済む。

**削除もしない。** SSO の設定が壊れたときの**唯一の復旧経路**になる
（ルートユーザーでのログインを除く）。

### ルート認証情報を作らない

Organizations の `CreateAccount` で作られたアカウントは、**ルートユーザーにパスワードが設定されない。**
ログイン手段が存在しないため、**MFA を掛ける対象そのものが無い。**

**この状態を維持する。** MFA を設定するには先にルートパスワードを作る必要があり、
それは**今より危険な状態を作ってから守る**ことになる。

組織では `RootCredentialsManagement` と `RootSessions` が有効になっているため、
本当にルート権限が要る場面（S3 バケットポリシーの復旧など）は
**管理アカウントから `sts assume-root` で短期セッションを取得する**ことで対応できる。
**常設の認証情報を持つ理由が無い。**

確認すべきなのは「MFA が設定されているか」ではなく、
**「パスワードとアクセスキーが存在しないままか」**である。

### Budget を最初に入れる

長期運用するアカウントなので、**課金の暴走を検知する仕組みを最初に置く。**

ADR 010 の想定は月 $13.45。これを超えるとしたらインスタンスタイプの誤り・
リソースの消し忘れ・Neon の課金開始のいずれかで、どれも早く気づきたい。
約50%の余裕を見て **$20** を閾値とした。

### SCP は今は入れない

リージョン制限などのガードレールを掛けられる状態になったが、**最初は入れない。**
SSM や IAM といったグローバルサービスの扱いで詰まるケースがあり、
**構築中に原因の切り分けを難しくする**ため。動いてから検討する。

## 認識しているリスク

| リスク | 内容 | 対処 |
|---|---|---|
| **管理アカウントからのバックドアは残る** | `OrganizationAccountAccessRole` により、管理アカウントの管理者は Shelfie アカウントの管理者になれる | **Organizations の構造そのもの**であり避けられない。「分離すれば管理アカウントから隔離される」わけではないことを理解した上で受け入れる |
| **ルートメールの受信箱が攻撃面になる** | ルート認証情報を持たない構成のため、残る起点は**パスワードリセットの経路**である | ルートメールに使う個人アカウント側で MFA を有効にする |
| **プロファイルの指定漏れ** | `--profile` を忘れると既定のプロファイルが向いている**共用アカウントにリソースを作ってしまう** | 作業開始時に `AWS_PROFILE` を設定し、`aws sts get-caller-identity` で確認する手順を [infra/README.md](../../infra/README.md) に明記した |

## 未決の論点

**この ADR では決めない。**

- **既存ワークロード（`tofu-blog` / `tottoku`）の分離** — 今回は移設しない。必要になったときに判断する
- SCP の内容 — 稼働後に検討する
- ステージング用アカウント — 要件が出てから

---

## 再検討のトリガー

- **ステージング環境が必要になったとき** — `shelfie-stg` を足す
- **管理アカウントからの分離では不十分な要件が出たとき**（第三者に権限を渡すなど）
- 既存ワークロードも分離することになったとき — OU の設計を含めて組み直す
